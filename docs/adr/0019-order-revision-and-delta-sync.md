# Server-authoritative order concurrency and delta sync

PostgreSQL is the authority for every non-draft order change. Each command carries the exact order revision the operator saw; the server atomically rejects a stale revision with `409 Conflict` and the current order, rather than allowing a silent overwrite. This uniform rule includes notes-only edits and excludes only additive receipt-print records and draft autosaves.

Connected foreground tablets keep their local order copies current with a bounded cursor-based delta pull every 5 seconds, with catch-up after reconnect. This rollout starts with orders only; inventory and all other app areas remain later slices. Supabase Realtime is not used: the existing authenticated Express delta endpoint provides complete, ordered recovery without a second client credential or authorization path. Awareness never decides whether a write is valid; the database does.

## Decisions

- Reads are local-first: render a saved local copy immediately, then check in the background. A screen with no saved copy while offline shows an explicit unavailable-offline state, never a spinner, blank page, or invented data.
- A first-ever tablet setup is the exception: keep the app unavailable until the complete historical order cache is downloaded. It shows one truthful phase-based setup screen and a clear waiting-for-connection state if interrupted. It resumes automatically from its saved position when connectivity returns and retains a visible Retry action. If the tablet lacks storage for the complete cache, setup stops with a clear explanation rather than silently trimming or accepting partial history. Later login, reconnect, and foreground change checks remain non-blocking. App-wide skeletal loaders are a separate later slice.
- Order history is a full cache of every order visible online, including visible historical and cancelled orders, rather than a recent or viewed-only working set.
- The current cache is store-wide device state shared by every authorized account on a tablet. Before any role gains restricted data visibility, cache ownership and access must be redesigned around the actual permission boundaries; no role-specific cache model is assumed today. No additional device-lock or app-level encryption requirement is introduced in this scope. The current native storage remains the permanent full-history store without a required sizing gate or SQLite migration.
- The existing single header sync status communicates connectivity, outgoing unsent changes, and incoming updates. It can show `Updating · N waiting`; a noticeable check says `Checking for updates…`, while `Updated just now` appears only after data actually changed.
- An order changed while an operator is editing remains editable with a stale-edit warning; the app never replaces the form or merges remote changes mid-edit. A non-editing order view updates immediately without a spinner, with the header sync status providing the acknowledgement. A filtered order list also updates immediately, removing a row that no longer matches and briefly stating where it moved.
- If the server rejects the later save as stale, the app shows the authoritative current order and explains that the local change was not saved. The operator deliberately re-enters any still-valid change; there is no automatic retry or merge. A bulk selection that changes elsewhere remains visibly selected and blocks confirmation until the operator reviews the changed order and deliberately removes it; the action then names the reduced selection exactly.
- A bulk order action commits per order, not as one all-or-nothing transaction: an order that goes stale in the final moment before submission fails on its own, while the rest of the already-reviewed batch still commits. The result names exactly what happened — how many committed and which order was skipped — and the operator can open a skipped order to see its current state, the same treatment as any other stale-write rejection.
- The foreground order-change check backs off when the server is unreachable rather than continuing to poll every five seconds through a known outage, and returns to the five-second cadence immediately once connectivity is confirmed again. It runs for as long as the app is open, on every screen, not only while an orders screen is visible.

## Considered options

- **Read scope:** viewed-only pages, a recent-history window, or administrator-selected retention were rejected in favour of the complete online-visible order history; they would make a legitimately needed order unavailable during an outage. Unlocking a new tablet after only its reference data arrives, opening it with no setup state, and a generic spinner were also rejected; it must finish the complete history download first. Exact percentage and count were deferred because the existing server path does not provide them. Manual-only retry and restarting the download from the beginning were rejected; automatic resumable recovery preserves the work already completed. Silent history trimming and partial-cache access were rejected because the cache promise is complete history.
- **Cache ownership:** separate account-specific caches were considered because Leyble-Hub will eventually have roles and permissions. They were deferred because those permission boundaries and their permitted data are not yet defined; each account would otherwise download the same full store data while adding repeated setup, storage, and recovery complexity. Clearing data at logout was rejected because it breaks offline store handoffs. The shared cache is an explicit temporary policy, not a role-security design.
- **Cache protection:** a device-lock baseline and app-level, hardware-backed encryption were considered because complete order history and customer data live on the tablet. Both were deferred from this scope; the current storage approach gains no new explicit security requirement.
- **Storage growth:** measuring representative full-history capacity before release and migrating to native SQLite now were both considered. They were rejected; the current native storage remains the chosen permanent store without a sizing requirement.
- **Change awareness:** a 20-second check was viable but slower than desired. A Supabase Realtime channel as a near-instant nudge was deferred: it would still need cursor catch-up, adds a second authorization and connection path, and provides no concurrency authority. The five-second foreground delta pull is the simple current choice. A whole-app rollout and an orders-plus-inventory rollout were deferred; orders alone prove the safety-critical pattern before expansion.
- **Sync presentation:** separate inbound and outbound indicators, a generic `Updating` label for every check, and per-screen updating banners were rejected. One calm header status is simpler; it distinguishes checking from an actual completed update without hiding the unsent-change count.
- **Stale-write scope:** exempting notes or building field-level merging was rejected. The normal order edit sends items, notes, and personnel together, and a uniform revision rule is safer and easier to explain. Receipt-print records and draft autosaves remain excluded because they are additive or single-device working state.
- **An order changing mid-edit:** immediately replacing the form would discard work, while automatic merging could create an unsafe hybrid. The selected warning preserves typing until a deliberate save attempt. For a non-editing view, a manual reload banner and a blocking replacement confirmation were rejected; immediate in-place truth is clearer. Retaining a row until manual refresh, or keeping it under a filter it no longer matches, was rejected because the list must remain truthful.
- **After a stale-save rejection:** retaining a side-by-side old form or automatically reapplying its contents was rejected. Showing the current order and requiring deliberate re-entry keeps the operator, not the app, responsible for deciding what remains valid.
- **Bulk selections:** silently removing a changed order, submitting every selected order and reporting a server-side partial result, and cancelling the whole selection were rejected. A visible stale-selection review prevents a false impression that an order was included while retaining unchanged selections.
- **Bulk action atomicity:** an all-or-nothing transaction across the whole batch was rejected; it would let one order gone stale in the final moment block a batch whose other orders were never in dispute, undoing the earlier decision to preserve an otherwise-valid selection rather than punish it for one bad order. Silently applying the successful orders with no summary was rejected as hiding a real outcome the operator needs to know; a blocking dialog enumerating every skipped order was rejected as too heavy for what is typically a single straggler.
- **Check backoff and scope:** continuing to poll every five seconds through a known outage was rejected as needless load with nothing to gain while the server is unreachable; stopping outright and waiting on a manual retry was rejected as too easy to leave stale once the connection actually returns. Scoping the check to pause outside order-related screens, and a hybrid of a slower app-wide cadence with a faster rate only on order screens, were both rejected in favour of one consistent cadence for as long as the app is open.
